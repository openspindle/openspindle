# Workspace model

The workspace is what the user works on: plates, the tool and stock libraries, measured height maps, the project's design rules and its name. It is plain immutable data (`WorkspaceState`, `src/domain/workspace/workspace.ts`) changed only by commands. Code: `src/domain/**`.

## Plates

A plate is one setup on the machine bed and the program machined from it. Its `name` is empty until the user gives it one; until then it shows as "Plate N", numbered by its place in the workspace (`plateLabel`). The plate that replaces a new project's empty plate takes the name given to that one (`plates.add`).

- **Setup** (`PlateSetup`): the stock and where its minimum corner sits on the bed (`stockAnchor`; its X and Y can be kept relative to a stored anchor, `stockRelativeTo`, like the work origin's), **one work origin** (`workOrigin`, the program's NC zero, in bed coordinates; its X and Y can be kept relative to a stored anchor, `workOriginAnchor`, which it follows when the anchors change; a plate with an [auto Z-height](auto-z-height.md) keeps its Z on the stock top, where the touch sets work Z0: `applyCommand` holds every plate a command brings in or changes to that, `withTouchedWorkOrigin`), **one assist policy** (vacuum, air, bed cleaning, anti-static on Run), the fixtures (each a snapshot of its definition, whose model is bundled with the app, a box or in the [Models library](models.md), and its placement, which a lock keeps and whose X and Y can be kept relative to a stored anchor, `relativeTo`; a wasteboard is one), the device the plate is set up for, and a snapshot of that device's anchors. Every operation machines from the plate's work origin.
- **Setup items** (`src/domain/plate/setup-items.ts`): what the 3D view selects and moves: the machine's bed (a bed fixture lies on it and covers its holes), the enabled fixtures with a model (wasteboards among them), the stock and the design (the program at its work origin), each with its mount points in bed coordinates. `plate.moveItem` moves a fixture by its position, the stock with the work origin, or the work origin alone; beds and locked fixtures stay in place.
- **Fixtures** (`src/domain/plate/plate-fixtures.ts`): the fixture commands hold a plate's fixtures to their rules; `plate.setup` does not change them. A plate has one bed: `fixture.setBed`, and `fixture.add` with a bed, keep the plate's own fixture of that bed's definition as it is (enabled), or else add the new one, and every other bed goes. A locked fixture (`isLocked`; beds stay in place without a lock) refuses `fixture.update` (a move, a turn, another origin or anchor) and `fixture.remove` until `fixture.lock` unlocks it. A plate holds at most 32 fixtures (`FIXTURE_LIMIT`, which also bounds a device profile's definitions). `fixtures.useDefaults` gives the plate its device profile's fixtures and anchors, keeping its locked fixtures.
- **Tool table** (`tools`): the plate owns the T numbers. Each entry maps a number to a library tool (`toolId`), or to none yet. Entry `null` is the implicit tool of a program that selects none. T0 is always the probe, and T9999 the 3D probe, as the Z1 firmware numbers them.
- **Operations**: the programs the plate runs, in order.
- **Groups**: named selections of program sections, by stable section id.
- **Notices**: what an import changed, until the user dismisses them.

A new project starts with an empty plate 1: the selected device profile's bed and fixtures, without stock or operations. It is a placeholder (`example`): the first plate of the user's own replaces it, and plates that replace the empty one keep its fixtures, device and anchors (`useImportContext`). A plate added with + in the Plates header replaces nothing (`useAddPlate`): it has the default stock on the selected profile, and goes after the empty plate, which stays as a plate of the user's own (`plate.keep`). Once stock is set up on the empty plate, the plates that replace it keep its whole setup (`keptSetup`): the stock and where it sits, and the work origin. That holds for generated and plugin operations and for plain NC programs, over the stock their CAM markers describe; exported plates keep their own setup. A probing operation machines nothing and brings no stock: added over the empty plate, it keeps that plate's setup as it is, and a new plate it starts has none (`targetPlate` in `src/app/workspace/defaults.ts`).

## Operations

An operation has a name, a revision (incremented on every change, so a plugin saving against an older revision is refused), a Pause before switch, its tool bindings and a source:

| Source          | NC                                                                                                                                                                        | Phase         |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- |
| `file`          | the imported NC, byte for byte unless importing split or fixed it; without its closing park when `park` is off; one from Fusion 360 keeps its `origin` to be updated from | machining     |
| `template`      | generated from a plugin's gcode-template program and the saved parameter values                                                                                           | the program's |
| `plugin`        | generated by the plugin (null until it has, which blocks Run)                                                                                                             | the plugin's  |
| `auto-level`    | generated from its parameters when compiling, so it can never go stale                                                                                                    | setup         |
| `auto-z-height` | generated from its parameters and the plate's work origin when compiling                                                                                                  | setup         |
| `auto-scan`     | traces the plate's toolpath bounds, derived when compiling                                                                                                                | setup         |
| `probe-3d`      | generated from its parameters when compiling: the 3D probe's routine                                                                                                      | setup         |

Each source kind is registered in `src/domain/operations/kinds.ts` with how it resolves to NC (and what that NC may contain: a probed grid for auto-level, a touch-off for auto Z-height, an outline traced with the probe for auto-scan, a corner or centre found with the 3D probe for 3D probing, no probing otherwise), its phase, whether a lone operation may be emitted byte for byte, what it validates while editing, and what it checks before Run against the connected machine. Kinds resolve and validate with the kit of the plate's machine (`kitForPlate`, `src/domain/fixtures/catalog.ts`: the kit of the plate's device, else the one its fixtures come from, else the default kit a new workspace starts from), whose probe the probing kinds measure with. The probing kinds place their start as setup items keep their points: relative to the probe position or to a stored anchor, with X and Y from the anchor and, for 3D probing, a Z on the bed (`ProbePlacement`, `src/domain/probing/placement.ts`). Their forms edit it with the fields the work origin, the stock and fixtures use (`ReferencePointFields`, `src/components/workspace/reference-point-fields.tsx`).

## Tools

`bindTools` binds an operation's own tool numbers (the T words its NC selects) into the plate's table:

- an existing binding stays;
- the probe slots keep their number: T0 is always the probe, T9999 the 3D probe;
- a library tool already in the table is reused, so the machine never changes to the same tool twice;
- otherwise the operation's own number is taken if free, then the tool's post-processor number, then the lowest free number.

An imported NC program prefers, for each of its tool numbers, the library tool it describes (Makera CAM's tool markers, else Fusion-style tool comments; `describedPreferences`, which rules tools out by diameter and kind and ranks them by name and flute length), else the tool with that post-processor number, which Fusion 360 imports skip.

`tool.assign` puts a library tool in an entry (merging into the entry that already holds it); `tool.renumber` moves an entry to another free number and rewrites every binding, refusing to move one to or from a probe slot. Deleting a tool from the library changes no plate: the entry keeps pointing at it, a diagnostic blocks Run and offers to assign another tool. The probe slots must hold a probe and no other entry may (`isProbe` in `src/domain/tools/tool-table.ts`, which compares a tool's kind as loosely as `toolKindKey` does, so "Probe" and "probe" are the same kind everywhere); either mismatch is its own diagnostic with the same fix.

A tool's `shaft` holds segments (a height and the diameters at both ends) that stack from the shoulder up, such as the taper from the flutes to the shank; Fusion 360 imports read them from the record's Shaft tab. A tool's photo (`image`) is a picture the app bundles or one chosen from a file, scaled to 480 pixels and kept in the tool as a WebP data URL. Its 3D model (`model`) is likewise a binary glTF the app bundles (`/models/….glb`) or one chosen from a file and kept as a data URL (at most 1 MB; `validateGlb` checks it is one self-contained GLB), in glTF's metres, Y up, with the tip at the origin.

Tool records are version 4. Records of versions 2 and 3 are upgraded when read (`upgradeTool` in `src/formats/tool-library/upgrade.ts`), a version at a time: version 3 records gain an empty 3D model, and in version 2 records the fields version 3 added (the shaft, photo, vendor description and grade; the maximum diameter, upper radius, tapered and thread tips and through-tool coolant; the holder's product link; the presets' description, cutting speed, ramp angle, transition and retract feeds and feed-per-revolution mode) come from the tool's Fusion record as an import reads it, keyed as a new tool's, so a saved catalog tool still equals its catalog record. An imported tool keeps that record (`source.raw`) as provenance only: nothing but this upgrade reads it.

`toolShape` (`src/domain/tools/tool-shape.ts`) turns a tool's dimensions into solids of revolution, in millimetres above its tip: the flutes, which cut (a probe's ball, which touches), and the shaft (a neck up to the shoulder length, the shaft's segments, then the shank up to the overall length), which must not touch the work. Each tool type has its cutting end (flat or corner-rounded, ball, drill point, chamfer or V cone, taper, round-over, thread teeth, or the ball on a lollipop mill's neck or a probe's stylus); a dimension the record leaves out falls back to one it gives (a shank as wide as the cutter, flutes one diameter long, a nominal length when the tool's is unknown). The tool's holder is not part of the shape. The tool library draws these shapes, each once, with three.js (`src/features/tool-library/tool-pictures.ts`), and keeps the pictures (`src/app/tools/tool-picture-cache.ts`). Tool cards show a tool's kept thumbnail and need no renderer: the library draws one a card asks for, and every library tool's in the background, and a plugin's view gets it with the tool (`picture`). During playback the 3D view shows the tool in the spindle (`toolRuns` in `src/features/viewer/viewer-plate.ts`, from each tool change on) at the end of the revealed path, or, while **Play** runs the moves, where it is along the move under way, and the probe where it probes: at a grid's active sample and a touch-off's point, since its NC reaches them with moves in machine coordinates. A tool with a 3D model is drawn from the model instead, in its own materials, once it has loaded (the 3D view loads each once per viewer, `ViewerAssets.toolModel`); its dimensions still give its shape.

## Compiling

`compilePlate(plate)` is pure, never throws and is cached per plate object. It compiles for the plate's machine: what is its own, such as its clearance, its work offsets, its probe's blocks and its CAM's markers, comes from the plate's kit (`kitForPlate`). It returns the program, a span per operation, program sections, pause points and diagnostics. A plate whose operations did not change keeps its program object and sections while its NC text and name stay the same, so moving the stock or the work origin parses nothing again and the 3D view keeps the uploaded path. A program is at most 1,000,000 lines (`MAX_PROGRAM_LINES`), well above what 10 MiB of NC holds.

- **Verbatim**: a plate with a single operation of a verbatim kind, identity tool bindings and no Pause before emits that NC byte for byte.
- **Work origin**: a work origin kept relative to a stored anchor starts the program with the kit's work offset NC (`workOffsetNc`) at the anchor's machine position plus the offsets, so its plate is always composed; its Run check needs anchors read from the connected device. On the Z1 that is `; Work origin: …`, `G21 G54` and `G10 L2 P0 X… Y…`: `G21 G54` comes first because the firmware reads G10's X and Y in the current units and `P0` is the current work coordinate system, whatever the program before left.
- **Compose**: otherwise each operation is emitted after a header (`; Operation: name`, `G21 G90 G17 G94`, the machine's clearance retract, `M5 M9`, and `M0` when it pauses before), with T words rewritten through its bindings and program ends removed; the program ends with the same modes, retract and `M5 M9`, then `M2`, so no job ends with the tool in the cut. The retract is the machine kit's `clearanceRetract` (`G53 G0 Z-3` on the Z1, the clearance Makera configures): a tool the operation before left in the cut rises out of it still turning, then the spindle stops, and the next operation's first move cannot drag it. It follows the modes, as the firmware reads a `G53` move's Z in the current units. An operation's NC may set only the modal state that header restores (units, distance mode, plane, feed mode), plus the blocks the kit reads as its own (`readNcBlock`): its probe's routines, only in the probing operations, and on the Z1 path control (`G61`, `G61.1`, `G64` with optional `P`/`Q`, alone in its block), as the Z1 firmware has no path control and corners by junction deviation (`M205`), so it changes nothing that could carry into the next operation, and `M400`, the extractor port (`M851` with an optional `S`, `M852`), the light (`M821`, `M822`) and the beeper (`M861`, `M862`), each alone in its block. It may end with the machine's park after its last move, a block the kit tells (`isPark`) and reads as its own: on the Z1 `G28` alone in its block, as Makera's CAM ends its programs, for which the firmware lifts Z to its clearance height, then moves X and Y to its clearance position. Anything that moves after a park is refused, and on the Z1 so is `G28` with other words. An NC file's **Park after machining** (`park`) keeps its closing park or leaves those lines empty, in either mode.
- **Sections**: tool changes, toolpaths, probing and other blocks, with ids stable across edits of other operations and tool renumbering (`operationId/kind:name#n`; a tool change is keyed by the operation's own T number). The kit's probe tells its grids and touch-offs, and the markers of its CAM start and name toolpaths (Makera CAM's `;@MKR|TOOLPATH` on the Z1, `src/domain/fixtures/makera-z1/makera-cam.ts`); without them, CAM headings in comments do, as does a comment on a line of its own after a blank line or before a tool change, where Fusion 360's posts name their operations. The G-code list heads them and the Job tab's stages read them; the job's position and the timeline's markers name them with their operation, "Isolation · Toolpath 1" (`positionLabel`). The timeline also marks the pauses compiling adds before operations, and is built once per compiled program (`buildPreviewTimeline`). A group keeps the sections that still exist; one whose sections are all gone is not shown.
- **Lines that cannot run**: every reader takes a line's words from one lexer (`readNcBlock`, `src/machine/contract/nc-block.ts`), which Run's dialect uses too: comments in parentheses or after `;`, words of a letter and a number, M117's text as data, even after a line number, and `%`. A line with an unclosed or unmatched comment, a transport checksum, a block-delete `/`, text that is not NC words or a number out of range cannot run as written: the preview does not draw it and Run refuses the program. Combining refuses its operation (`operation-unsafe`); a program emitted byte for byte reports its first such line as an error (`nc-unreadable`).
- **Toolpath bounds**: `plateToolpathBounds` (`src/domain/compile/toolpath-bounds.ts`) is where a plate cuts: the feed moves that are not the probes', of its operations outside the setup phase, each measured from its own NC. The 3D view outlines it and snaps to it; Fit grid, Center and auto-scan use it ([auto-scan.md](auto-scan.md#toolpath-bounds)).
- **Pause points**: Pause before, auto-level review and the NC's own M0/M1. The Makera dialect sends program stops as `M600` at transfer time.
- A broken operation reports a diagnostic and does not stop the others from compiling.

## Diagnostics

Everything that blocks or qualifies Run is a `Diagnostic` (`src/domain/diagnostics.ts`): `error` or `warning`, a code, a message, what it is about (its `Subject`: the plate, `PlateSubject`; its setup's work origin, `PlateSetupSubject`; an operation, `OperationSubject`; or an entry of the tool table, `ToolSubject`), where it is when it has a place on the bed (`Place`: a `Point`, `Path` or `Area`, in bed coordinates) or lines in the compiled program, and optionally a quick fix. The probing kinds' rule modules report `Issue`s, diagnostics that do not yet know what they are about, which the operation kind makes its operation's. Diagnostics cover compile problems, unassigned or missing tools, a probe assigned outside a probe slot (T0, and T9999 for the 3D probe) or another tool assigned to one, stale, missing or incompatible plugins, auto-level, auto Z-height and 3D probing placement and stock checks, auto-scan's outline and order, and a machining operation whose cuts in X and Y all run below the stock or all above it (its program's Z zero is not where the work origin puts it: with the work origin on the stock bottom, a program cutting down from Z0 on the stock top would cut through the stock; `src/domain/compile/stock-depth.ts`). `plateDiagnostics` gathers them for the Prepare inspector and the Job tab's run checklist, and keeps them per plate object while the tools and plugins stay the same; the operation kinds' run checks add what depends on the connected machine (for example that an anchored auto-level grid uses anchors read from it).

`keyDiagnostics` keys a plate's diagnostics by code and subject, so a problem keeps its key through edits that change its message. The Prepare 3D view marks every problem with a place where it is (`ProblemView` draws a ring at a point, a line along a path and an area's outline, in the severity's colour; a marker over it names the problem on hover): an auto Z-height's touch point off the stock, an anchored auto-level grid, auto-scan's outline beyond the stock, and a machining operation's cuts below or above the stock. Picking a marker selects what the problem is about and shows it (`src/features/viewer/problem-focus.ts`): the view draws it stronger, highlights its program lines while its operation stays selected, and pans to it when it is near an edge or out of view. **Show** in the inspector and in the design rule results shows a problem the same way.

## Design rules

The project's design rules (`DesignRules`, `src/domain/design-rules/rules.ts`) are limits on a plate's compiled moves (max cutting feed, plunge rate, cut depth and depth under the stock, the spindle stopped while cutting, rapid moves into the stock) and program rules (`ProgramRule`, `program-rules.ts`), which find what a machine would not run as written in each operation's own NC and resolve it: the common ones and the kit's (`programRulesFor`). Each is reported as an error or a warning, or ignored. `checkDesignRules` (`check.ts`) measures the moves over the stock's box, widened by each tool's radius (without stock, below Z0 over the extent of its cuts). Its violations are `Diagnostic`s per rule and operation, with the program lines they concern, where the worst move ends, and for an NC file's program rule a `resolve-rule` fix. They are not part of the plate's diagnostics: the Job tab's run checklist blocks Run on an error, and nothing blocks export. Importing asks about the program rules' issues (`src/app/workspace/import-plan.ts`). `designRules.set` changes the rules; they are saved with the project, kept across reloads and count as unsaved changes ([design-rules.md](design-rules.md)).

## Commands

`applyCommand(state, command)` is the only writer: it returns the next state or a reason. Commands cover plates (add, remove, select, move, rename, setup, move a setup item, dismiss a notice), fixtures (add, remove, update, lock, set the bed, use the device's defaults), operations (add, remove, move, rename, pause before, source with an expected revision, a plugin's tool assignments), the tool table (assign, renumber), groups, the libraries, saving the project (its file and the plugin references it keeps for plugins that are not installed), height maps, the design rules, anchor synchronisation, replacing the whole workspace (opening a project) and batches that apply several commands atomically. `WorkspaceStore` wraps it in a TanStack Store.

## Undo and redo

`WorkspaceStore` records the user's edits in a `History` (`src/app/workspace/history.ts`) for **Edit › Undo** and **Redo**: each step is the workspace before and after an edit, which share everything the edit left alone. Every command is an edit except the selection (`plate.select`), what the device reports (`anchors.sync`, `heightMap.store`), saving (`project.saved`) and dismissing a notice (`plate.dismissNotice`); a batch is an edit when it holds one, and the libraries restored from storage are dispatched with `record: false`. Those other changes outlast undo and redo: restoring a step's workspace replays the ones made after it (one that no longer applies changes nothing), and the selected plate stays selected while the restored workspace has it.

- An edit that leaves everything but the selection as it was is no step, and the workspace keeps its parts.
- Edits of one value merge into one step while each comes within a second of the one before: a plate's or an operation's name, a setup field (by the fields it sets), a fixture's placement (by the fields it sets) and its lock, the plate's bed, an operation's source and tools (as a plugin view saves them), a plate's groups, the design rules and each library. Any other edit, an undo or a redo starts a new step.
- A new edit drops the steps undone, and the history keeps the last 200. `workspace.replace` (opening or starting a project, a reload restoring its workspace) starts a new history.
- A restored workspace keeps the identity of its parts, and a change replayed on the workspace it was first made on gives the same result, so a project undone back to how it was saved has no unsaved changes (`hasUnsavedChanges` compares by identity).
- A removal's or a move's notification, and the tool library's Undo delete, undo their own step only while it is the latest (`WorkspaceStore.undo(step)`); after later edits they say so.

The Device tab's fixture library (`FixtureLibraryStore`) has a history of its own: edits of a profile's definitions (typing a fixture's name merges by field) and its alignment are steps; the selected profile and what a device reports are not, and the library restored from storage starts a new history. Plates set up for a device follow the anchors an undo or a redo restores, as they follow an alignment.

Undo and Redo reach the history of the section on show: the workspace's on Prepare and Job, the fixture library's on Device. With a text field focused they undo its typing instead; a focused plugin view (a frame of its own) or the developer tools undo their own typing, which the main process asks of them; and while a dialog is open only typing is undone.

## Storage and files

- **No stored project**: every launch starts with a new project on the stored tool and stock libraries (`src/persistence/library-document.ts`), which the app keeps on its own; library edits are not project changes. Closing the window with unsaved project changes asks to save them first ([projects](step-nc-projects.md)). Reloading it (⌘R, or the dev server after a code change) keeps the workspace and its unsaved changes, in memory only ([architecture](architecture.md)). Projects and exported NC this version cannot read, from a newer version or in a format before version 4, are refused with a message.
- **Exported NC** carries the plate as a leading comment block (the plate envelope, [plate-definition.md](plate-definition.md)); an export whose NC was edited afterwards imports as a single program with a notice.
- **Projects** are STEP-NC files holding the workspace and references to the plugins its operations use ([step-nc-projects.md](step-nc-projects.md)).
- **Tool library files** (`exportToolLibrary` and `importToolLibrary`, `src/formats/tool-library/library-file.ts`): an export is a zip of `tool-library.json`, the native library (`{"format": "openspindle-tool-library", "version": 2, "units": "mm", "tools": […]}`), and each photo and 3D model its tools keep, stored once (`images/1.webp`, `models/1.glb`): a tool names the file by its path relative to the JSON instead of holding a data URL, and bundled pictures and models keep their `/images/…` and `/models/…` paths. An import reads these archives, the JSON of earlier versions, and Fusion 360's JSON, `.tools` and ZIP libraries. It turns each named file back into a data URL before the tool is read like any other (upgraded, then checked), refuses a named file the archive lacks, and checks every 3D model as a chosen one is (`validateGlb`: one self-contained GLB). The limits are what memory allows rather than what 10,000 tools could hold (a 300 KB photo and a 1 MB model each, 13 GB): a 256 MB file, 160 MB of JSON (16 KB a tool) and 384 MB unpacked, which as data URLs (a third larger) is the 512 MB the app stores a library in. Reading an archive (`src/lib/zip.ts`) streams it: the central directory is read with at most 65,535 entries, handling ZIP64 or refusing it clearly, and each entry is inflated a few kilobytes at a time against these limits and the photo's or model's own, stopping as soon as its real decompressed bytes would pass one — whatever the entry's own stated size claims — and its length and CRC-32 are checked before it is used; only stored and deflated entries are read, and any other method is refused. An import that would take the library past 10,000 tools is refused, and so is an export an import would refuse.
