# Running programs

Run is explicit and lives only on the Job tab. Preparing, previewing, importing or adding a program never sends it to a machine. The request is `{id, name, source, assists}` with a fresh UUID; a used ID is never replayed. A program is at most 10 MiB and 1,000,000 lines, a file sent to the machine at most 4 MiB and 250,000 lines (`RUN_LIMITS`); a longer program is sent in [parts](#programs-sent-in-parts).

## Dialect normalization

`machine.prepare` shows exactly what the firmware will execute, one output line per source line so line numbers stay aligned with the Job tab's G-code listing. The Makera dialect (`firmware/makera/dialect.ts`):

- reads each line with the lexer the preview and compiling share (`readNcBlock`): strips `;` and parenthesized comments and `%` lines; M117 text stays verbatim, after a line number too;
- **removes leading `N` line numbers** — the dispatcher skips numbered blocks, so keeping them would silently skip the block;
- **uppercases** lines made only of NC words — the firmware's `has_letter` is case-sensitive and lowercase-first lines are console commands. A lowercase line that is not NC (for example `abort`) is rejected;
- **turns `M0`/`M1` into `M600`** — the Z1 has no M0 handler; M600 suspends playback until `resume`;
- **adds the tool number to an `M6` without one** — the firmware changes tools only for an `M6` with its T word on the same line and ignores a bare `M6`, so the probe or old tool would stay in and `M3` would halt (pcb2gcode writes `T1` and `M6` on separate lines). The number is the one the last T word selected; an `M6` with none selected is rejected;
- **leaves out an `M0`/`M1` right after a tool change** — the Z1 stops for a change by hand itself, so it would be a second stop (Makera Studio sends it to a firmware that ignores it);
- **adds the spindle speed to an `M3` or `M4` without one** — the firmware sets the speed only from an S in the `M3`'s own command; an S on a line of its own or on a move sets none, so a bare `M3` runs at the speed set before, 10,000 rpm after boot (pcb2gcode writes `S12000` or `G00 S12000`, then a bare `M3`). The speed is the last S word the program set, as written and as the preview reads it, but not an S another code takes (`M223`'s rpm override, `G4`'s seconds). It goes right after the M code, or before it on a line such as `T1 M3`, which the firmware runs as one command that ends at the first S after its M code. An `M3` before any S is sent as it is, and a line the speed takes past 63 bytes is rejected;
- rejects unclosed and unmatched comments, block-delete lines, transport checksums, text between words that is not NC words, numbers out of range, non-ASCII, control characters, lines over 63 bytes and first letters outside G/M/T/S/X/Y/Z/A/F/O. The preview does not draw a line the lexer refuses, and the plate reports it ([workspace-model.md](workspace-model.md#compiling)).

Every rewrite is listed (`changes`) and the pause lines are reported, so the Job view can show them.

Preparing a long program takes most of a second (about 0.7 s for 10 MiB), so the machine process prepares programs on a worker thread, where it holds up neither status polling nor Stop. The controller keeps the last four prepared programs by their source text, which Run uses too, a check asked for while the same program is being prepared waits for that one, and it never prepares the running job's program again while the job lasts. Run checks again, once its program is prepared, that the machine still takes it. The Job tab keeps its check while the program is unchanged, however long the tab stays closed.

## The Job tab

The Job tab previews the selected plate and runs it interactively: the job panel on the left, the 3D view and its timeline in the middle, the G-code and the console on the right. At the top of the job panel, in view above everything else in it, are the connected device's card, as in Prepare, and the toolbar with the job's controls: **Run** before a job, then what the job allows (**Pause**, **Resume**, **Confirm installed**, **Stop**), then **Dismiss** once it has ended, with the job's status beside them. Under it the panel shows the run as stages, one card each: the checks before Run, the upload, every operation of the plate and the end. The stage the job is in shows its prompt (a tool change, a pause, the height-map review) or its progress; the others stay compact, done, up next or not run. Stopped or failed, the operation it ended in says so.

- **Run checklist** (the first stage; the checks that pass fold away): device connected, plate compiles, tools assigned, operations up to date, design rules met (no errors; [design rules](design-rules.md)), plate matches the machine (for example an anchored probing operation, or a work origin kept relative to an anchor, needs anchors read from the connected device), program transfers (the dialect accepts it) and machine ready (`availability.run`). Run is enabled only when every check passes; a failing check offers its fix (a link to Prepare, **Show in Prepare** for the design rules, or **Read anchors**, which also moves a plate set up for another device to the connected one; [stored anchors](stored-anchors.md)).
- **Job session**: Run snapshots the plate as run (its compiled program, pause points and tool table), so the view stays consistent if the plate is edited during the job. Dismiss clears it once the job has ended.
- **Preview**: the timeline, or a line picked in the G-code, shows the program up to that line. **Play** runs the machine's moves from there ([firmware-preview.md](firmware-preview.md)), each at its feed as the machine's firmware keeps it (on the Z1, rapids at 2000 mm/min until the program sets another), at the playback speed (0.25× to 100×): the tool moves along the path, drawing it as it goes. Pause keeps its place; at the end the whole program shows again. Acceleration, dwells and the waits at tool changes and pauses are left out, so the time it plays is not the job's (`moveTimes` in `src/domain/nc/move-times.ts`).
- **Live follow**: while the job runs, the timeline, the 3D view and, on the [simulator](device-controls.md#development-simulator), the camera panel follow the machine. Each status report (polled once a second) is placed on the moves of the line it reports: at the point nearest the machine, by its machine position and by its work position, and nearest where the playhead is, so a path that passes the same place twice is followed along. The playhead then goes there over about the time until the next report, so it follows one report behind, along the path; at a tool change the tool waits at the change position, as the tool being taken out. Scrubbing detaches until **Back to live**. The G-code listing shows exactly what the machine receives, marks lines the dialect changed and pause points, and shows stripped comments muted.
- **Work origin**: a dot on the shown plate's bed marks where the connected machine keeps work zero ([device-controls.md](device-controls.md#status)), and a card at the 3D view's lower right gives it relative to the plate's work origin, in X, Y and Z, with the tool offset (T). It reads zero where the machine is set up as the plate expects, so a work origin elsewhere shows before Run: for example with a plate whose work origin is not kept relative to an anchor, whose program sets at most work Z and leaves work X and Y wherever the machine has them.
- **Console**: under the G-code, the commands the app sent and the machine's replies as they happen, with notes for connecting, Stop and the job's phases, and a command line to send the machine one line ([device-controls.md](device-controls.md#protocol-trace-and-console)).
- **Tool change**: when the machine waits for a tool, its stage names the requested T number and the plate's tool for it, and a **Change tool** dialog shows that tool and the operation the job resumes with. **Confirm** there, or **Confirm installed** in the toolbar, confirms the change; **Dismiss** only closes the dialog. Neither is offered on machines with an automatic tool changer.
- **Measurements**: what the machine measures shows on its operation's card: where a touch-off touched the stock top, in machine and in work X and Y, and set work Z0, a height grid filled in point by point and then its height map and spread, the contacts of a 3D probing routine as they come and then where it set the work origin, the top it touched and a pocket's or boss's size, and each tool measured at the tool sensor. The machine reports them only from its own routines, whose lines reply to every connection, even from a played file: its Z probe and auto-leveling (`M495`, which the Z1 firmware's [Z probe](touch-off.md) always runs and its [Height map](height-map.md) runs from a stored anchor with the work origin kept relative to one), its 3D probing (`M480`, which the Z1's [3D probing routines](3d-probing.md) run) and its tool changes. The Z probe's touches show once its routine ends, as a corner routine outside the stock touches the top the same way before it searches across X and Y; the routines that run unechoed, the other 3D probing ones, report contacts outside any routine state (`M497`), which are theirs. Probing written as `G38.2` or `G32` in the program, as Surface touch and the other height maps are, reports nothing, as the lines a file plays reply to a null stream. The reported line moves only while a feed move runs (the player reports the last `G1`/`G2`/`G3` block's line), so a measurement or tool request is placed on the first operation, from the one reached so far, that probes or changes to that tool.
- **Pauses**: a pause is matched to the plate's pause point at or before the reported line: Pause before an operation, the NC's own program stop, or a height map's review. The review reads the height map once (M375.1, display only), analyses it ([height-map.md](height-map.md)) and offers Retry read; Resume and Stop are in the toolbar.
- **Depth of cut**: under the timeline, the line on show gets the tool in the spindle, the predicted depth and width of cut of its moves, and how far below the stock top they leave the tool's tip. A worker sweeps the plate's stock with each tool's shape in program order, as a height field (`src/domain/tools/cut-engagement.ts`): what a stretch of travel removes that earlier moves left is its engagement, from the tip up to the highest stock it takes and across its direction of travel. A cut that takes the tool's whole width at that depth (a slot, a V-bit's groove) gets that width exactly; a partial one is as accurate as the height field's cells, which are finer the narrower the program's cuts and coarser for a long program with large tools. Nothing is cut from below, rapid moves and the probe are taken to stay clear of the stock, and a plate without stock is taken to reach down from Z0.
- The workspace header shows the job's phase on the other tabs, and a red dot beside **Job** in the tab strip shows that a job is under way.

## Transaction

The unique file `/sd/gcodes/openspindle-<uuid>.nc` (`openspindle-<uuid>-<n>.nc` for each part of a program sent in parts) is uploaded, read back and played once, from the folder where Makera Studio keeps the programs it runs. Data and motion are never retried.

1. **Preflight** — `G28.6` with its acknowledgement (every reported axis homed: unhomed, `play` answers `ERROR:Machine has not been homed` and halts the machine), then a fresh status passing the run rules: Idle, no program, released emergency stop, spindle stopped, milling mode, bed-clean mode reported.
2. **Assists** — each requested mode is sent, acknowledged and confirmed by a newer status.
3. **Upload** — B0 `upload`, B1 MD5, the device's B2 view request (answered with block count and 8192-byte block size), consecutive B3 blocks, B4 completion (empty or exactly `ok\r\n`). One MD5 challenge is allowed. Status polling pauses.
4. **Readback** — B0 `download`, the advertised MD5 is compared when it is a digest (stock firmware may send a placeholder), then **every byte** is read back and compared. The transfer ends with the device's own B4 after ours, which closes the file; nothing else is sent before it, so a part uploaded next never meets it.
5. **Final preflight** — homed axes and run rules again; assists must still match.
6. **Tool reset** — the firmware skips `M6 T<n>` when it believes T<n> is already in the spindle: no stop for the tool and no measurement at the tool sensor. So on a machine that changes tools by hand, when the program changes tools before it starts the spindle, `M493.2 T-1` (no tool) is sent and confirmed by a status reporting none. The program's first change, the probe's included, then always stops for the tool to be installed and measures it. Not with an automatic tool changer, which tracks the clamped tool and with none set would pick the new one without dropping the old; not when the program starts the spindle first, since the firmware halts `M3` without a cutting tool. A job that then does not start leaves the machine with no tool, so its next tool change measures again.
7. **Play** — exactly one `play <path>`, as Makera Studio sends it. On the Z1 the controller has no file access: `play` makes the player ask the ESP32 for the file by a CRC of its name, and once the ESP32 serves it the player answers `File size <bytes>` and streams it. The CRC has 16 bits, so another file on the card can answer to the same name: the size, which comes before player progress, must be the part's. Another size while the part starts fails the job with that reason, and the machine is stopped as by Stop. The ESP32 is not open source; when it does not serve the file, nothing is reported at all. Without `-v` the replies to played lines are discarded, as they are for Makera Studio. The job starts only when status reports player progress (P); a failure line (`Currently printing`, `File name CRC check failed`) refuses the start. An unconfirmed start keeps following the machine and is abandoned as `unverified` after 30 s without progress.

Stop during steps 3–4 cancels the transfer (B5) before halting. Each step has a 10 s deadline and the whole preparation 80 s for each file sent.

## Completion

The firmware's rounded percentage reaches 100 while the last blocks still execute, and an Idle report can come from an M5 dwell while the program still runs. So completion follows the player lifecycle (`firmware/makera/completion.ts`):

| Phase            | Evidence                                                                                                                                                                |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| running / paused | P present; Tool → tool-change wait (with the requested tool), Pause → program pause (at an M600 line, reported as the line before it) or hold (user pause), Hold → hold |
| finishing        | the done snapshot: P at 100% with the prepared line count                                                                                                               |
| cleaning         | P gone after the done snapshot with bed cleaning on; waits for `Done ATC` after it and Idle                                                                             |
| **completed**    | P gone after the done snapshot, Idle, spindle stopped, no abort evidence and no machine errors                                                                          |
| stopped          | Stop was requested and the machine aborted (Alarm)                                                                                                                      |
| failed           | Alarm, a halt or abort line without our Stop, or machine errors during the program                                                                                      |
| unverified       | P disappeared without the done snapshot                                                                                                                                 |
| lost             | the connection dropped; the machine may still be running                                                                                                                |

Finishing (30 s) and cleaning (180 s) that take too long are marked overdue but stay tracked. Errors and alarms the machine reports during the program are recorded as job faults with their line; errors of individual played lines are not reported without `-v`. The poller runs at 4 Hz near the end so the one-second done snapshot is not missed.

While a job streams, only light, beep, overrides, pause, resume and tool confirmation are admitted, and height-map and anchor reads are deferred until it ends. At a program pause the height map can be read (M375.1 is display-only), which is how a height map's review works.

## Programs sent in parts

A program larger than a file the machine takes at once is sent in parts (`makeraParts`, `firmware/makera/parts.ts`), cut only before a tool change (`M6` with its T word, which the dialect adds where the source leaves it out), each part holding as many whole tool changes' work as fits. When the lines from one tool change to the next alone make too large a file, Run refuses the program and names those lines. The prepared program lists its parts (`PreparedProgram.parts`); the run checklist says how many, and the G-code list marks where each begins.

- **Joins.** A part after the first starts with the modal state the program had reached at its cut: units, distance mode, plane, work coordinate system and feed. `play` resets the player to G90 and the firmware keeps the rest from the file before, but the part says them itself. The spindle speed needs no restating: the dialect has put it on the `M3` that starts the spindle after the part's tool change. A part that ends with the spindle running ends with `M5`, so the machine reports it done and idle. Nothing else is added: the next part's tool change follows, where the Z1 stops the spindle anyway.
- **Upload first.** Every part is uploaded and read back (steps 3–4 for each) before the first plays, so nothing fails to transfer mid-job.
- **Bed cleaning.** The Z1 treats the end of every file it plays as a finished job: it beeps and, with bed cleaning on, sweeps the bed at the height the part ended. So the parts before the last play with bed cleaning off and the last with the plate's setting, where `device` gives back what the machine was set to before the run. A job that ends before its last part leaves bed cleaning off.
- **Next part.** When a part completes (the evidence above: P gone after the done snapshot, idle, spindle stopped), the next plays at once, after the same preflight as before any play and the last part's bed cleaning. The firmware refuses a `play` within a second of the previous file's end, which completion already waits out. Nothing is retried: the tracker gives each part to one start (`claimNext`), a part that does not start ends the job with the reason before anything else can start it, and Stop between parts ends the job too.
- **One job.** `PartedCompletion` (`core/parted-completion.ts`) follows each part with the firmware's tracker and reports the job in program lines: the line a part's file reports maps back to the program, progress runs over all parts by their size, elapsed time adds up, and faults and measurements accumulate. `JobState.part` names the part being sent or played. Between parts the job stays active, so jogging, homing and reads wait for it.

Programs sent in parts are verified against the development simulator, not on a machine ([Status and safety](../README.md#status-and-safety)).

## Per-plate assists

`assists` has four keys — `vacuum`, `blow`, `bedClean`, `antiStatic` — each `"device"`, `"on"` or `"off"`. `device` sends nothing; explicit modes use `M331`/`M332` with suffixes none, `.1`, `.2` and `.4`. Explicit modes stay configured after the job; nothing is restored automatically. Bed cleaning runs after the done snapshot at the current Z: a composed program ends with the tool retracted to the machine's clearance ([workspace-model.md](workspace-model.md)), while a single NC file machined as imported ends wherever it leaves the tool. The app does not verify fixture clearance. A program sent in parts sets bed cleaning itself around its parts (above).

## Evidence

In [Makera's Z1 firmware](https://github.com/MakeraInc/MakeraZ1Firmware/tree/b3a2e26a9eaa2b01358f74ccdef549b993a08175):

- `Player.cpp` — `play_command` (homed check, `PTYPE_PLAY_START` with the name's CRC-16), `on_main_loop` (the ESP32's `PTYPE_PLAY_VIEW` and `File size`, printed before `playing_file` (which P needs) is set; played lines to a null stream without `-v`, done snapshot, 1 s `PLAY_FINISH_REPORT_WINDOW_US`, `set_job_complete`), `on_get_public_data` (the reported line: the running `G1`/`G2`/`G3` block's, else the last one saved), `abort_command` (abort snapshot for three polls), `suspend_command` (saves the lines played before an `M600`) / `resume_command`, M600/M601.
- `Robot.cpp` — `M0` does nothing (its case is commented out); `is_homed_all_axes`, which `play` asks, prints `ERROR:Machine has not been homed` and halts (`NON_HOME`) when an axis is not homed; an S on a `G0`–`G3` sets only the planner's laser power (`s_value`), and `G4`'s S is seconds to dwell.
- `SpindleControl.cpp` — `M3` sets the speed only from its own S (`set_speed`) and otherwise starts the spindle at the speed set before (`PWMSpindleControl.cpp`: `spindle.default_rpm`, 10,000 in `configZ1.default`); `M223`'s S is an rpm override; nothing in the firmware handles `M4`.
- `GcodeDispatch.cpp` — a line runs as commands split at G, M, S and T words, after a `G` line's first `G90`/`G91` is moved to its front; a command of only an S word has no G or M, and no module reads it.
- `SerialConsole.cpp` — play data line counting (`g_request_lines`, blank lines count).
- `Kernel.cpp` — P tuple, `get_state` (Idle when the conveyor is idle and the spindle off).
- `ATCHandler.cpp` — job complete → beep and `M486.1` bed cleaning, `Done ATC`; `M6` changes tools only with its T word on the same line; `on_main_loop` echoes its script lines to every connection and runs them with them as the stream, so its tool changes, calibrations and `M495` probing report even from a played file.
- Between played files (for parts): `Player.cpp`'s end of file stops, parks and resets nothing (no `M5`, `M9`, move or modal reset) and calls `set_job_complete` for every file; `play_command` refuses a play while `playing_file`, which stays set for the 1 s finish window; the `PLAY_VIEW` that starts a file sets `absolute_mode` (G90) and nothing else. Units, plane, feed, work offsets, the tool (kept in EEPROM with its length offset) and the auto-level grid (RAM, until a reset, `M370` or a new probe) carry over. `ATCHandler.cpp`'s `M6` for the tool already in the spindle only stops the spindle.

And in the [Carvera Community Controller](https://github.com/Carvera-Community/Carvera_Controller/tree/63da3c0a8ab6bca2563ff4c2aadb7ab5323335bf): `XMODEM.py` / `framing.py` — B0–B6 framing and readback; the ESP32 transfer side is not in the firmware.

On a Z1 Pro, upload and full readback of a harmless file are verified (B4 `ok\r\n` after upload and after readback). There, `play /sd/<file> -v` draws no reply and no progress, so Run plays without `-v`, as Makera Studio does: it uploads to `/sd/gcodes/` and plays from there, `File size` follows each play with the uploaded file's size in bytes, and played lines get no replies. A bare `M6` after `T1` changes no tool on the Z1, so the dialect puts the tool number on the `M6` ([Dialect normalization](#dialect-normalization)). Playing and completion are verified against the development simulator; see what the README lists as [not yet verified on a machine](../README.md#status-and-safety).
