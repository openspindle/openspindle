# Stored anchors

Prepare → Setup → **Anchor** places the stock by its front-left bottom corner, and each fixture's **Anchor** in Prepare → Fixtures places the fixture by its origin, the point named beside it ([models.md](models.md#origin)). **Relative to** lists the anchors the plate's machine stores, then **Custom position**. Choosing an anchor keeps the point's X and Y relative to it: the fields show and edit offsets from that anchor, Z stays on the bed, and changing the reference leaves the point where it is. **Custom position** is bed coordinates. The work origin's **Relative to** works the same way. A machine that stores no anchors shows no **Relative to**: its positions are custom. This is a workspace edit: it sends no motion, offset-setting or configuration-writing command.

Orange dots mark every saved anchor on each plate's bed. Hover shows the name and bed X/Y. Markers use the support bed height, independently of stock, wasteboards, toolpath origin and playback. They stay visible when covered by stock. Factory entries' names carry a **(default)** suffix; they are not presented as a successful device read.

Anchors come from the machine: its firmware adapter reads them (`FirmwareAdapter.anchors`) and reports a list of named machine positions (`AnchorConfiguration` in `src/machine/contract/anchors.ts`), each with an id that never changes, since plates refer to it. A machine whose adapter has no `anchors` reports `features.anchors: false`: nothing is read, the Device page shows no **Anchors** card unless its fixture kit places default anchors, and nothing is kept relative to an anchor. When the machine stores anchors, the app reads them once per verified idle connection. Makera's adapter reads four allowlisted configuration keys: `coordinate.anchor1_x`, `coordinate.anchor1_y`, `coordinate.anchor2_offset_x`, and `coordinate.anchor2_offset_y`. Anchor 2 is Anchor 1 plus the offsets; they are reported as `anchor-1` (Anchor 1) and `anchor-2` (Anchor 2). **Read anchors** on the Device page's **Anchors** card reads these values again or retries a failed read without reconnecting; the Job tab's run checklist and a plate's auto-level diagnostics offer it when a plate needs anchors read from the connected device, and there it also moves that plate to the connected device when it was set up for another. Its label changes to **Reading anchors…** during retrieval, and the workspace reports success or failure. Hover or keyboard focus explains why the action is disabled.

Makera's reads use `config-get sd <key>` to request the saved SD configuration explicitly. Only matching `sd: <key> is set to <number>` replies count as retrieved values; cache or factory replies are not accepted. Responses may arrive as normal text (`0x90`) or configuration text (`0x83`); configuration text stays isolated from control acknowledgements. Configuration errors (`0x85`) fail the read. On a Z1 Pro, the bare query returns `cached: coordinate.anchor1_x is not in config` on `0x83`, while the explicit SD query returns the saved value on `0x90`.

Reads require fresh Idle status with no active job and are serialized against controls, height-map retrieval and Run; Stop can interrupt them. Each key has an eight-second deadline. Explicit firmware errors are reported immediately, while incomplete or invalid results leave the connection available with a separate anchor error. Reading sends no motion or configuration writes. A retry starts a complete new read of every key; partially retrieved or previously cached values never count as a successful current read.

Device profiles retain the last successful configuration and the bed alignment. Plates contain independent snapshots. Once the connected device's anchors are read, every plate moves to that device and takes its anchors, whichever device it was set up for, and so does a plate opened or added while the device stays connected. A change on the Device page to the anchors of a device that is not connected, such as their alignment on the bed, moves only plates set up for it or for no device yet. Refreshing anchor definitions moves only what is kept relative to an anchor: the stock, a fixture or the work origin follows its anchor, keeping its X/Y offsets; if the anchor is gone, it stays where it is, in bed coordinates. Everything in bed coordinates stays where it is.

## Changing the anchors

**Edit** on the Device page's **Anchors** card changes where the connected machine stores its anchors: type an anchor's machine X and Y, or take where the machine is now (the locate button beside it). It is offered for the connected device's own anchors once they have been read. **Write to device** lists what changes and asks first; **Write anchors** writes every anchor, with the machine idle and no program running. Makera's adapter sends the four keys one at a time (`config-set sd <key> <value>`, to 0.001 mm, Anchor 2 as its offset from Anchor 1), requires each `sd: <key> has been set to <value>` reply and reads all four back. The plates then follow the anchors as after a read; the firmware's own moves, such as tool changes and the tool sensor, use them once the machine is reset. A write that fails part way leaves the anchors unknown until they are read again, and nothing is retried. Plugins cannot write anchors.

## Work origin from an anchor

A work origin kept relative to an anchor also sets the machine's work offset, as Makera's controller does before a job: the compiled program starts with `G21 G54` and `G10 L2 P0 X… Y…`, the anchor's stored machine position plus the origin's X/Y offsets. `G10 L2 P0` sets the current work coordinate system's X and Y origin, read in the current units, and the firmware saves G54 ([`Robot.cpp`](https://github.com/MakeraInc/MakeraZ1Firmware/blob/b3a2e26a9eaa2b01358f74ccdef549b993a08175/src/modules/robot/Robot.cpp#L568-L641)); `G21 G54` first makes those millimetres and G54, whatever the program before left. Z is not changed. With a factory snapshot these lines are preceded by a `FACTORY DEFAULT anchor coordinates` comment. Run requires, like an anchored auto-level grid, that the plate's anchors were read from the connected device (the plate's device) and still match its current stored anchors; otherwise **Plate matches the machine** fails with **Read anchors** as its fix. Other devices' plates keep their own markers. A failed read does not replace cached definitions with fabricated measurements.

## Coordinate registration

Anchors are machine positions. The viewer places them on the bed by where the first one is there (`anchor1BedPosition`), with the others calculated as:

`bedXY = machineXY − machineAnchor1XY + anchor1BedPosition`

A machine's fixture kit supplies that position with its factory anchors (`FixtureKit.factoryAnchors`); without a kit, the first anchor starts at the bed's origin. This is explicit model registration, not a discovered global machine-to-bed calibration. Device → Anchors → **… on bed** (named after the first anchor) adjusts that alignment for the physical installation; plates set up for that device follow. It changes display coordinates only; it never writes firmware configuration.

For the Makera Z1 (`MakeraZ1` in `src/domain/fixtures/makera-z1/makera-z1.ts`), the bed model has bounds −103…103 mm. The viewer translates it by +100, giving an outer minimum of −3 mm. The supplied L-bracket's 15 mm arms establish an inner stock corner at bed `[12,12]`, where the kit places Anchor 1. This follows the controller's anchor-relative convention: [Makera controller](https://github.com/MakeraInc/CarveraController/blob/3914c912452f83fbd5b5d90c730cb78795198438/src/makera.py#L1201-L1202) calculates a work position relative to Anchor 1 plus the bracket width. The extra −3 mm comes from this project's supplied-model coordinate frame.

The shipped Z1 defaults are Anchor 1 `[-192.4,-194.3]` machine mm and Anchor 2 offset `[88.5,45]`, producing default bed positions `[12,12]` and `[100.5,57]`, as in the firmware's [`configZ1.default`](https://github.com/MakeraInc/MakeraZ1Firmware/blob/b3a2e26a9eaa2b01358f74ccdef549b993a08175/src/configZ1.default#L405-L409). The firmware getter reads the saved SD configuration; changed configuration files may differ from motion values loaded at startup until the machine restarts. The app does not claim these anchors were physically measured.

## Portable setup

A plate's setup keeps its snapshot of the machine's anchors (`anchors`), which saved projects and the exported NC's plate envelope carry with it. It contains `version: 1`, the device identity, where the anchors came from (`factory` or `firmware-config`), the anchors' machine coordinates, the first anchor's bed position and, for a read, when it was fetched. `StoredAnchorSetupSchema` (`src/domain/anchors/stored-anchors.ts`) validates it: 1 to 32 anchors with IDs of their own, IDs and names of 1–200 characters without control characters, and machine and bed coordinates within ±10 m. NC instructions remain byte-preserved.
