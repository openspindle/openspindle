# Stored anchors

Prepare → Setup → **Anchor** places the stock by its front-left bottom corner, and each fixture's **Anchor** in Prepare → Fixtures places the fixture by its origin, the point named beside it ([models.md](models.md#origin)). **Relative to** lists the anchors the plate's machine stores, the first as the bed's origin (**Anchor 1 (bed origin)** on the Z1, [coordinate registration](#coordinate-registration)). Choosing another anchor keeps the point's X and Y relative to it: the fields show and edit offsets from that anchor, Z stays on the bed, and changing the reference leaves the point where it is. The bed origin is bed coordinates, which are offsets from the first anchor. The work origin's **Relative to** works the same way. A machine that stores no anchors shows no **Relative to**. This is a workspace edit: it sends no motion, offset-setting or configuration-writing command.

Orange dots mark every saved anchor on each plate's bed. Hover shows the name and bed X/Y. Markers use the support bed height, independently of stock, wasteboards, toolpath origin and playback. They stay visible when covered by stock. Factory entries' names carry a **(default)** suffix; they are not presented as a successful device read.

Anchors come from the machine: its firmware adapter reads them (`FirmwareAdapter.anchors`) and reports a list of named machine positions (`AnchorConfiguration` in `src/machine/contract/anchors.ts`), each with an id that never changes, since plates refer to it. A machine whose adapter has no `anchors` reports `features.anchors: false`: nothing is read, the Device page shows no **Anchors** card unless its fixture kit places default anchors, and nothing is kept relative to an anchor. When the machine stores anchors, the app reads them once per verified idle connection. Makera's adapter reads four allowlisted configuration keys: `coordinate.anchor1_x`, `coordinate.anchor1_y`, `coordinate.anchor2_offset_x`, and `coordinate.anchor2_offset_y`. Anchor 2 is Anchor 1 plus the offsets; they are reported as `anchor-1` (Anchor 1) and `anchor-2` (Anchor 2). **Read anchors** on the Device page's **Anchors** card reads these values again or retries a failed read without reconnecting; the Job tab's run checklist offers it when a plate needs anchors read from the connected device (for an anchored probing operation or an outline tracing edges, or a work origin kept relative to an anchor), and there it also moves the project to the connected device when it was set up for another. Its label changes to **Reading anchors…** during retrieval, and the workspace reports success or failure. Hover or keyboard focus explains why the action is disabled.

Makera's reads use `config-get sd <key>` to request the saved SD configuration explicitly. Only matching `sd: <key> is set to <number>` replies count as retrieved values; cache or factory replies are not accepted. Responses may arrive as normal text (`0x90`) or configuration text (`0x83`); configuration text stays isolated from control acknowledgements. Configuration errors (`0x85`) fail the read. On a Z1 Pro, the bare query returns `cached: coordinate.anchor1_x is not in config` on `0x83`, while the explicit SD query returns the saved value on `0x90`.

Reads require fresh Idle status with no active job and are serialized against controls, height-map retrieval and Run; Stop can interrupt them. Each key has an eight-second deadline. Explicit firmware errors are reported immediately, while incomplete or invalid results leave the connection available with a separate anchor error. Reading sends no motion or configuration writes. A retry starts a complete new read of every key; partially retrieved or previously cached values never count as a successful current read.

Device profiles retain the last successful configuration and the bed offset. All plates in a project share one device. Connecting adopts the connected device immediately using its stored profile, even before an anchor read succeeds. Choosing **Device** applies to the whole project, including while offline. Opening a saved project or reloading the window preserves its device choice during that connection. Later anchor reads refresh the project only when they belong to its device. Plates keep independent snapshots of the device anchors and their own bed setup anchors. Refreshing anchors moves only what is kept relative to one: stock, fixtures and the work origin keep their X/Y offsets; if the anchor is gone, they stay where they are in bed coordinates. Everything already in bed coordinates stays where it is.

## Bed setups

A device's profile holds one or more bed setups (Device → **Bed setup**; `BedSetup` in `src/domain/fixtures/profiles.ts`): references to shared fixture definitions, with their default placements and whether new plates enable them, plus anchors of its own such as a jig's corner. Fixture models and compatibility belong to the shared library, so using a fixture on another device requires no copy or upload. A profile starts with **Default**; **+** copies the bed setup shown, the bin removes it (a profile keeps at least one), **Name** renames it, and **Default for new plates** makes it the project's starting bed setup. A profile holds up to 20 bed setups.

A bed setup's anchors (**Anchors from Anchor 1**, up to 16) are X and Y from the device's first anchor, typed, or taken from where the connected machine is (the locate button). They are kept in the app, and on the device too when it stores them ([below](#bed-setup-anchors-on-the-device)), and move with the first anchor: recalibrating Anchor 1 moves them with it. A plate set up on a bed setup (`bedSetupId`) keeps its anchors in its snapshot after the device's, each at the first anchor plus its offset (`withBedSetupAnchors`, marked `bedSetup`), so **Relative to**, probing placements and the 3D view's markers offer them like the device's. Editing a bed setup's anchors moves the plates on it as a read of the device's anchors does: what is kept relative to one of them follows it.

Choosing **Device** in the Device page’s **Bed setup** card assigns every plate immediately and determines the device for new and imported plates. It works without a connection or an anchor read and can be undone from Prepare. Switching devices uses the destination’s default bed setup and stored anchors while preserving stock, operations and placed fixtures. There is no separate device selector on a plate. **Add fixture** offers every shared fixture compatible with the project’s machine type; a fixture need not be listed in a bed setup to be available.

**Bed setup** in Prepare lists the bed setups of the selected plate's device and sets the plate up on the one chosen: its bed and fixtures (the plate's locked fixtures stay) and its anchors. The button beside it, **Apply bed setup again**, does it again after the bed setup's fixtures changed; the bed and fixtures themselves are changed in the bed setup, on the Device page. A plate whose bed setup this computer does not have, such as one set up on another, shows **Not on this computer**, keeps its own anchors and offers **Add bed setup** beside it, which adds an arrangement to the device's profile and adds any missing fixture definitions to the shared library.

Before Run, a placement or work origin kept relative to a bed setup's anchor needs the device's first anchor, which it is kept from, to match the device's current stored anchors (`probing/anchors-changed`, `work-origin/anchors-changed`).

### Bed setup anchors on the device

**Store bed setup anchors on the device**, on the Device page's **Anchors** card (off by default, for each device: `storeAnchors` in its profile), has the device keep every bed setup's anchors in its configuration besides its own, so they stay with the machine. Their names and bed setups stay in the app. A read of the device's anchors reads them too, and the app writes them a second after they change, while the device is connected, idle and running no program; quick edits write once.

Makera's adapter keeps them after Anchor 1 and 2, one setting each from `openspindle.anchor3` on: the anchor's id and its X and Y from Anchor 1 to 0.001 mm (`openspindle.anchor3 <id>,45.500,19.000`), or `-` once the place is free. The firmware reads none of them (no setting it reads shares their keys' checksums). `config-set sd` cannot remove a setting, and overwrites one in place only while the new value is at most 19 characters longer than the one it was added with, so places stay: an anchor keeps its place, a new one takes the first free place, else a new setting after the last, and the place of a removed anchor is freed with `-`. A place that holds anything else is left alone. A read goes through the places up to the first `is not in config`, at most 32 (`ADDED_ANCHOR_LIMIT`); a write reads them first, sends each changed setting, requires each `sd: <key> has been set to <value>` reply and reads them back (`writeAnchorConfiguration` with `added`). The device stores at most 32.

What the device stored when last read or written (`storedAnchors`) tells the app's edits since from changes made on the device, such as by another computer (`storedAnchorsMerged`):

- An anchor the app has not changed since takes the device's position, and so does one the app has but the device never stored before: the device's is the one measured.
- An anchor changed in the app, such as one edited while the device was not connected, keeps the app's position, which is written next.
- An anchor removed in the app stays removed, and its place is freed.
- An anchor the device stores that the app has never had, such as one added on another computer, joins the profile's default bed setup, named by its place (`openspindle.anchor5` is **Anchor 5**).
- An anchor the app has that the device no longer stores, such as after its configuration was restored, stays, and is written again.

Switching it on reads nothing new: what the last read found is merged, and a write follows when the app's anchors differ. Switching it off forgets what the device stored; the settings stay on the device. A write that fails shows why on the **Anchors** card with **Write again**; the same anchors are not written again until they change. It leaves the device's own anchors as they were read.

## Changing the anchors

**Edit** on the Device page's **Anchors** card changes where the connected machine stores its anchors: type an anchor's machine X and Y, or take where the machine is now (the locate button beside it). It is offered for the connected device's own anchors once they have been read. **Write to device** lists what changes and asks first; **Write anchors** writes every anchor, with the machine idle and no program running. Makera's adapter sends the four keys one at a time (`config-set sd <key> <value>`, to 0.001 mm, Anchor 2 as its offset from Anchor 1), requires each `sd: <key> has been set to <value>` reply and reads all four back. The plates then follow the anchors as after a read; the firmware's own moves, such as tool changes and the tool sensor, use them once the machine is reset. A write that fails part way leaves the anchors unknown until they are read again, and nothing is retried. A finished Outside corner, Inside corner, Pocket center or Boss center in the Job tab writes the same way: **Save as anchor** keeps where it found its corner or centre as an anchor, the device's or one of the plate's bed setup ([corners and centres](3d-probing.md#in-the-job-tab)); **Probe anchor** on the **Anchors** card sets up such a probing, an Inside corner, to run.

## Work origin from an anchor

A work origin kept relative to an anchor other than the first also sets the machine's work offset, as Makera's controller does before a job, and so does one at the bed origin (in bed coordinates, offsets from the first anchor) once the plate's anchors were read from its device. The compiled program starts with `G21 G54` and `G10 L2 P0 X… Y…`, the anchor's stored machine position plus the origin's X/Y offsets. `G10 L2 P0` sets the current work coordinate system's X and Y origin, read in the current units, and the firmware saves G54 ([`Robot.cpp`](https://github.com/MakeraInc/MakeraZ1Firmware/blob/b3a2e26a9eaa2b01358f74ccdef549b993a08175/src/modules/robot/Robot.cpp#L568-L641)); `G21 G54` first makes those millimetres and G54, whatever the program before left. Z is not changed. With a factory snapshot these lines are preceded by a `FACTORY DEFAULT anchor coordinates` comment. A work origin at the bed origin on factory anchors, or on another device's, sets nothing: work X and Y are then the machine's own, set on Device. Run requires, like an anchored probing operation, that the plate's anchors were read from the connected device (the plate's device) and still match its current stored anchors; otherwise **Plate matches the machine** fails with **Read anchors** as its fix. A failed read does not replace cached definitions with fabricated measurements.

## Coordinate registration

Anchors are machine positions, and the first is the bed's origin: bed coordinates are millimetres from it (`machineToBed`),

`bedXY = machineXY − machineAnchor1XY`

with Z 0 where the machine's fixture kit puts it. Once Anchor 1 is calibrated on the machine, a bed position is where the machine goes, without an offset to add. The kit places its bed and fixtures from Anchor 1 (`FixtureKit.factoryAnchors` gives the anchors themselves until they are read). Device → Anchors → **Bed offset** moves the machine's own bed (its model and holes) from where the kit places it, for an installation whose bed sits elsewhere from Anchor 1; plates set up for that device follow. It changes display coordinates only; it never writes firmware configuration. Fixtures, the MDF bed among them, keep their own positions.

For the Makera Z1 (`MakeraZ1` in `src/domain/fixtures/makera-z1/makera-z1.ts`), Anchor 1 is the supplied L-bracket's inner corner: its 15 mm arms put the bracket's outer corner at bed `[-15,-15]`. Z 0 is the MDF bed's top, which the bracket stands on; the aluminium bed's top is at Z −6. The 200 × 200 mm work area starts at bed `[-12,-12]`, and the bed model (bounds −103…103 mm) is translated by `[88,88,-6]`. This follows the controller's anchor-relative convention: [Makera controller](https://github.com/MakeraInc/CarveraController/blob/3914c912452f83fbd5b5d90c730cb78795198438/src/makera.py#L1201-L1202) calculates a work position relative to Anchor 1 plus the bracket width.

Projects before format 9, plate exports before version 8 and fixture libraries before version 3 had the work area's front-left corner as the origin, with Z 0 on the aluminium bed: Anchor 1 sat at their `anchor1BedPosition` (`[12,12]` from the kit) and the MDF top at Z 6. Opening them moves every bed position by those amounts (`upgradeBedFrame`, `LEGACY_BED_FRAME`), keeps a non-default `anchor1BedPosition` as the bed offset, and turns points kept relative to Anchor 1 into bed coordinates; their programs do not change.

The shipped Z1 defaults are Anchor 1 `[-192.4,-194.3]` machine mm and Anchor 2 offset `[88.5,45]`, putting Anchor 2 at bed `[88.5,45]`, as in the firmware's [`configZ1.default`](https://github.com/MakeraInc/MakeraZ1Firmware/blob/b3a2e26a9eaa2b01358f74ccdef549b993a08175/src/configZ1.default#L405-L409). The firmware getter reads the saved SD configuration; changed configuration files may differ from motion values loaded at startup until the machine restarts. The app does not claim these anchors were physically measured.

## Portable setup

A plate's setup keeps its snapshot of the machine's anchors (`anchors`), which saved projects and the exported NC's plate envelope carry with it. It contains `version: 2`, the device identity, where the anchors came from (`factory` or `firmware-config`), the anchors' machine coordinates, the bed offset (`bedOffset`) and, for a read, when it was fetched. `StoredAnchorSetupSchema` (`src/domain/anchors/stored-anchors.ts`) validates it: 1 to 32 anchors with IDs of their own, IDs and names of 1–200 characters without control characters, and machine and bed coordinates within ±10 m. NC instructions remain byte-preserved.
