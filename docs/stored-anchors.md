# Stored anchors

Prepare → Setup → **Anchor** places the stock by its front-left bottom corner, and each fixture's **Anchor** in Prepare → Fixtures places the fixture by its origin, the point named beside it ([models.md](models.md#origin)). **Relative to** lists the anchors the plate's machine stores, the first as the bed's origin (**Anchor 1 (bed origin)** on the Z1, [coordinate registration](#coordinate-registration)). Choosing another anchor keeps the point's X and Y relative to it: the fields show and edit offsets from that anchor, Z stays on the bed, and changing the reference leaves the point where it is. The bed origin is bed coordinates, which are offsets from the first anchor. The work origin's **Relative to** works the same way. A machine that stores no anchors shows no **Relative to**. This is a workspace edit: it sends no motion, offset-setting or configuration-writing command.

Orange dots mark every saved anchor on each plate's bed. Hover shows the name and bed X/Y. Markers use the support bed height, independently of stock, wasteboards, toolpath origin and playback. They stay visible when covered by stock. Factory entries' names carry a **(default)** suffix; they are not presented as a successful device read.

Anchors come from the machine: its firmware adapter reads them (`FirmwareAdapter.anchors`) and reports a list of named machine positions (`AnchorConfiguration` in `src/machine/contract/anchors.ts`), each with an id that never changes, since plates refer to it. A machine whose adapter has no `anchors` reports `features.anchors: false`: nothing is read, the Device page shows no **Anchors** card unless its fixture kit places default anchors, and nothing is kept relative to an anchor. When the machine stores anchors, the app reads them once per verified idle connection. Makera's adapter reads four allowlisted configuration keys: `coordinate.anchor1_x`, `coordinate.anchor1_y`, `coordinate.anchor2_offset_x`, and `coordinate.anchor2_offset_y`. Anchor 2 is Anchor 1 plus the offsets; they are reported as `anchor-1` (Anchor 1) and `anchor-2` (Anchor 2). **Read anchors** on the Device page's **Anchors** card reads these values again or retries a failed read without reconnecting; the Job tab's run checklist offers it when a plate needs anchors read from the connected device (for an anchored probing operation, or a work origin kept relative to an anchor), and there it also moves that plate to the connected device when it was set up for another. Its label changes to **Reading anchors…** during retrieval, and the workspace reports success or failure. Hover or keyboard focus explains why the action is disabled.

Makera's reads use `config-get sd <key>` to request the saved SD configuration explicitly. Only matching `sd: <key> is set to <number>` replies count as retrieved values; cache or factory replies are not accepted. Responses may arrive as normal text (`0x90`) or configuration text (`0x83`); configuration text stays isolated from control acknowledgements. Configuration errors (`0x85`) fail the read. On a Z1 Pro, the bare query returns `cached: coordinate.anchor1_x is not in config` on `0x83`, while the explicit SD query returns the saved value on `0x90`.

Reads require fresh Idle status with no active job and are serialized against controls, height-map retrieval and Run; Stop can interrupt them. Each key has an eight-second deadline. Explicit firmware errors are reported immediately, while incomplete or invalid results leave the connection available with a separate anchor error. Reading sends no motion or configuration writes. A retry starts a complete new read of every key; partially retrieved or previously cached values never count as a successful current read.

Device profiles retain the last successful configuration and the bed offset. Plates contain independent snapshots. Once the connected device's anchors are read, every plate moves to that device and takes its anchors, whichever device it was set up for, and so does a plate opened or added while the device stays connected. A change on the Device page to the anchors of a device that is not connected, such as its bed offset, moves only plates set up for it or for no device yet. Refreshing anchor definitions moves only what is kept relative to an anchor: the stock, a fixture or the work origin follows its anchor, keeping its X/Y offsets; if the anchor is gone, it stays where it is, in bed coordinates. Everything in bed coordinates stays where it is.

## Changing the anchors

**Edit** on the Device page's **Anchors** card changes where the connected machine stores its anchors: type an anchor's machine X and Y, or take where the machine is now (the locate button beside it). It is offered for the connected device's own anchors once they have been read. **Write to device** lists what changes and asks first; **Write anchors** writes every anchor, with the machine idle and no program running. Makera's adapter sends the four keys one at a time (`config-set sd <key> <value>`, to 0.001 mm, Anchor 2 as its offset from Anchor 1), requires each `sd: <key> has been set to <value>` reply and reads all four back. The plates then follow the anchors as after a read; the firmware's own moves, such as tool changes and the tool sensor, use them once the machine is reset. A write that fails part way leaves the anchors unknown until they are read again, and nothing is retried. A finished 3D probing operation in the Job tab writes the same way: **Save as anchor** keeps where it found its corner or centre as an anchor ([3D probing](3d-probing.md#in-the-job-tab)).

## Work origin from an anchor

A work origin kept relative to an anchor other than the first also sets the machine's work offset, as Makera's controller does before a job, and so does one at the bed origin (in bed coordinates, offsets from the first anchor) once the plate's anchors were read from its device. The compiled program starts with `G21 G54` and `G10 L2 P0 X… Y…`, the anchor's stored machine position plus the origin's X/Y offsets. `G10 L2 P0` sets the current work coordinate system's X and Y origin, read in the current units, and the firmware saves G54 ([`Robot.cpp`](https://github.com/MakeraInc/MakeraZ1Firmware/blob/b3a2e26a9eaa2b01358f74ccdef549b993a08175/src/modules/robot/Robot.cpp#L568-L641)); `G21 G54` first makes those millimetres and G54, whatever the program before left. Z is not changed. With a factory snapshot these lines are preceded by a `FACTORY DEFAULT anchor coordinates` comment. A work origin at the bed origin on factory anchors, or on another device's, sets nothing: work X and Y are then the machine's own, set on Device. Run requires, like an anchored probing operation, that the plate's anchors were read from the connected device (the plate's device) and still match its current stored anchors; otherwise **Plate matches the machine** fails with **Read anchors** as its fix. Other devices' plates keep their own markers. A failed read does not replace cached definitions with fabricated measurements.

## Coordinate registration

Anchors are machine positions, and the first is the bed's origin: bed coordinates are millimetres from it (`machineToBed`),

`bedXY = machineXY − machineAnchor1XY`

with Z 0 where the machine's fixture kit puts it. Once Anchor 1 is calibrated on the machine, a bed position is where the machine goes, without an offset to add. The kit places its bed and fixtures from Anchor 1 (`FixtureKit.factoryAnchors` gives the anchors themselves until they are read). Device → Anchors → **Bed offset** moves the machine's own bed (its model and holes) from where the kit places it, for an installation whose bed sits elsewhere from Anchor 1; plates set up for that device follow. It changes display coordinates only; it never writes firmware configuration. Fixtures, the MDF bed among them, keep their own positions.

For the Makera Z1 (`MakeraZ1` in `src/domain/fixtures/makera-z1/makera-z1.ts`), Anchor 1 is the supplied L-bracket's inner corner: its 15 mm arms put the bracket's outer corner at bed `[-15,-15]`. Z 0 is the MDF bed's top, which the bracket stands on; the aluminium bed's top is at Z −6. The 200 × 200 mm work area starts at bed `[-12,-12]`, and the bed model (bounds −103…103 mm) is translated by `[88,88,-6]`. This follows the controller's anchor-relative convention: [Makera controller](https://github.com/MakeraInc/CarveraController/blob/3914c912452f83fbd5b5d90c730cb78795198438/src/makera.py#L1201-L1202) calculates a work position relative to Anchor 1 plus the bracket width.

Projects before format 9, plate exports before version 8 and fixture libraries before version 3 had the work area's front-left corner as the origin, with Z 0 on the aluminium bed: Anchor 1 sat at their `anchor1BedPosition` (`[12,12]` from the kit) and the MDF top at Z 6. Opening them moves every bed position by those amounts (`upgradeBedFrame`, `LEGACY_BED_FRAME`), keeps a non-default `anchor1BedPosition` as the bed offset, and turns points kept relative to Anchor 1 into bed coordinates; their programs do not change.

The shipped Z1 defaults are Anchor 1 `[-192.4,-194.3]` machine mm and Anchor 2 offset `[88.5,45]`, putting Anchor 2 at bed `[88.5,45]`, as in the firmware's [`configZ1.default`](https://github.com/MakeraInc/MakeraZ1Firmware/blob/b3a2e26a9eaa2b01358f74ccdef549b993a08175/src/configZ1.default#L405-L409). The firmware getter reads the saved SD configuration; changed configuration files may differ from motion values loaded at startup until the machine restarts. The app does not claim these anchors were physically measured.

## Portable setup

A plate's setup keeps its snapshot of the machine's anchors (`anchors`), which saved projects and the exported NC's plate envelope carry with it. It contains `version: 2`, the device identity, where the anchors came from (`factory` or `firmware-config`), the anchors' machine coordinates, the bed offset (`bedOffset`) and, for a read, when it was fetched. `StoredAnchorSetupSchema` (`src/domain/anchors/stored-anchors.ts`) validates it: 1 to 32 anchors with IDs of their own, IDs and names of 1–200 characters without control characters, and machine and bed coordinates within ±10 m. NC instructions remain byte-preserved.
